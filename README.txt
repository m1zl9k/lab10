Задание на «подумать головой» (Защита лабораторной)
Студент обязан аргументировать аномалии в отчете:
> 1. **Состояние сна:** Почему сервер, находясь в состоянии ожидания подключения на шаге accept(), потребляет ровно 0% процессорного времени? Опишите механизм перевода потоков в планировщике ядра из состояния *Running* в *Waiting/Sleeping*.  
> 2. **Анализ сетевых таблиц ядра:** Откройте новое окно консоли во время падения сервера с ошибкой «Address already in use» и выполните системную команду просмотра сетевых структур ядра: netstat \-ano | findstr 9999 (в Windows) или ss \-ap | grep 9999 (в Linux). Зафиксируйте флаг состояния. Почему порт занят, если программа сервера уже закрыта?  
> 3. **Аппаратное исправление:** Раскомментируйте строку server\_socket.setsockopt(...) в коде сервера. Повторите эксперимент с быстрым перезапуском. Объясните, что делает флаг SO\_REUSEADDR на уровне таблиц портов ядра ОС.


1. accept() - блокирующий syscall. Ядро проверяет очередь соединений сокета. Если пусто - переводит поток из Running в Waiting (TASK_INTERRUPTIBLE в Linux), убирает из run queue, кладёт в wait queue сокета. Планировщик больше не даёт потоку кванты -> CPU = 0%. Когда приходит SYN и handshake завершается - ядро будит поток, возвращает в run queue.

2. netstat -ano | findstr 9999 показывает TIME_WAIT на порту 9999. Это защита TCP: ядро держит структуру сокета 2×MSL (1–4 мин), чтобы запоздавшие пакеты старого соединения не попали в новое. Программа закрыта, но структура сокета в ядре жива → bind() возвращает EADDRINUSE / [WinError 10048].

3. Устанавливает флаг в структуре сокета в ядре. При bind() ядро видит флаг и разрешает привязку к порту в TIME_WAIT. Старое соединение продолжает ждать 2×MSL, новый сокет получает свою структуру на том же порту. TCP различает их по 4-кортежу. Против LISTENING другого процесса на Windows не помогает.
